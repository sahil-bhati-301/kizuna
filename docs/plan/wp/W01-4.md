# W01-4: Normalisation library
Tier: A · Size: M · Implementer: implementer-core · Estimate: 9% weekly
Depends on: W01-1 · Branch: wp/W01-4-normalise
Spec refs: docs/specs/pipeline.md#33-content-pipeline-and-data-quality (Normalisation rule → arch §3.3); docs/specs/content.md#31-core-content-entities (radical variant forms → arch §3.1)

## Goal
One pure library that every parser uses for Unicode, kana, reading markers and radical variants, so the same text always normalises the same way.

## Acceptance criteria (each must be testable)
1. All text is NFC; applying the normaliser twice gives the same result as once (idempotent).
2. Kana: katakana converts to hiragana for storage and back for on'yomi display, round-tripping for every kana in the Unicode kana blocks except a listed set (for example ヴ, small ヵ/ヶ) with documented handling.
3. Reading markers: `た.べる` → stem `た`, okurigana `べる`; leading or trailing `-` sets prefix or suffix flags; malformed input (two dots, empty stem) returns a typed error, not an exception.
4. Radical variants map to their Kangxi number through a checked-in table (氵 → 85 水, 亻 → 9 人, 扌 → 64 手, 忄 → 61 心, 艹 → 140 艸, 辶 → 162 辵, and the rest). Position-dependent forms (阝: left → 170 阜, right → 163 邑) need a position; without one they return an "ambiguous" result.
5. The library is in `src/domain/` and passes the domain purity rules (no I/O, no clock, no RNG).

## Out of scope
- Furigana alignment (W02-3). Romaji. KRADFILE substitute characters (W01-5 uses this table).

## Packages and files expected to change
- apps/pipeline/src/domain/normalise/… (kana, markers, nfc, radicals, data table)

## Test plan
- Unit: marker cases, error cases, each variant in the table, 阝 with and without position.
- Property: NFC idempotence; hiragana ↔ katakana round-trip over the kana blocks; output of marker parsing re-joins to the input.
